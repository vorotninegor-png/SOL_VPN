# SOL VPN: окно оплаты, FAQ и VIP

## Изменённые файлы и поведение

- `app.js`: рублёвые карточки, единая кнопка «Оплатить», Bottom Sheet,
  bot-first ЮKassa и ручной fallback; FAQ/админские обработчики;
- `index.html`: окно оплаты, новый FAQ, кнопки и белые SVG админки;
- `style.css`: изолированные стили окна, Liquid Rise и VIP-переход;
- `config.example.js`: публичные настройки FAQ без изменения рабочего config.js;
- `tests/payment-methods.cjs`, `tests/stars-checkout.cjs`,
  `tests/info-faq.cjs`, `tests/admin-users.cjs`, `tests/payment-expiry.cjs`: локальные проверки;
- `FAQ_RELEASE.md`, `ADMIN_VIP_RELEASE.md`, `PAYMENT_EXPIRY_UI.md`,
  `RELEASE_NOTES.md`: подробности.

Версии `app.js` и `style.css` — **5007**. Новые библиотеки не добавляются.
Существующие скидки, названия/особенности тарифов, VPN и навигация сохранены.

## Оплата

Все тарифные карточки показывают цену в рублях из `data.tariffs[].price_kopecks`.
Нижняя кнопка Telegram содержит только «Оплатить» и открывает окно выбора:
ни заказа, ни платёжного запроса при этом нет. Для обычного браузера без
MainButton есть одна собственная нижняя кнопка.

Окно поднимается/закрывается за 330 мс, фон затемняется и размывается на 7 px.
Есть крестик, нажатие снаружи, свайп вниз по заголовку, Escape/Back и ограничение
Tab внутри окна. Уменьшение движения отключает анимации. Быстрое переоткрытие
не оставляет страницу заблокированной.

После выбора Stars работает прежний `openInvoice` и проверка серверного
статуса. Клиентское `paid` не выдаёт подписку. При закрытии окна во время
создания поздний invoice не открывается сам; сохранённая попытка остаётся.

ЮKassa создаёт заказ только по явному выбору метода. Backend отправляет
покупателю сообщение с кнопкой «Перейти к оплате». `checkout_delivery.sent`
показывает предложение открыть чат бота. При `failed/unknown/pending/unavailable`
доступен ручной переход: GET статуса **того же заказа**, проверка ID/провайдера/
валюты/суммы/HTTPS, затем `openLink`. Новый заказ из fallback не создаётся.
Если окно закрыто до ответа, браузер позднее не открывается автоматически.
GET/bootstrap восстанавливают delivery state после перезапуска/очистки storage.

Карточки показывают актуальный тариф, существующий платёж сохраняет свою цену.
Если цены расходятся, у конкретного метода видна отметка «Ранее созданный счёт»
и пояснение: оплате подлежит сумма на кнопке выбранного метода. Старый счёт
не пересоздаётся и не переоценивается браузером.

После создания заказа сервер возвращает неизменяемый `expires_at` и текущее
`server_time`: таймер 10:00 не зависит от выбора тарифа, часов устройства или
повторного входа. Последние 60 секунд имеют мягкую янтарную подсветку без мигания.
После «Время оплаты истекло» приложение проверяет старый заказ перед явным
созданием нового. Статус checkout отделён от финансового: проверенная поздняя
оплата учитывается один раз. Скидка потенциально оплачиваемого старого счёта
удерживается до проверки, поэтому новый счёт может иметь полную цену.
Детали интерфейса — PAYMENT_EXPIRY_UI.md, сервера — PAYMENT_EXPIRY.md.

Коэффициент `STARS_RUB_PER_STAR=2` и live Stars не изменяются. ЮKassa остаётся
выключенной до отдельного согласования магазина, фискализации и допустимости
такой продажи цифровой услуги по правилам Telegram. Внешний checkout не снимает
требование Telegram использовать Stars; способы сокрытия оплаты не добавлены.

## FAQ и VIP

Новый вопрос о Stars — третий; ссылки точные, названия ботов в строках не
показываются. Вариант №2 по умолчанию выключен, его условия требуют отдельной
проверки. Публичные флаги нужно **добавлять** в существующий config.js, сохранив
его реальный API URL; не заменять его файлом-примером с api.example.com.
Перед публикацией ссылки требуют проверки условий и рекламной квалификации,
а при применимости — настоящих данных рекламодателя/ERID. Они не выдуманы.
Это условие публикации, а не утверждение, что правовая проверка уже выполнена.

Сервер различает административный VIP и независимые права. Золотая кнопка
означает admin grant, а не любой effective VIP. Старые `is_vip=1` без истории
источника сохраняются как защищённые: после первой миграции список назначенных
VIP может быть пуст, хотя их доступ сохраняется в общем списке. Для отзыва
таких старых прав нужна отдельная квалификация истории оператором. Обычная
кнопка не отменяет оплаченные месяцы, ключи, неизвестный или иной VIP.
На старом API без provenance-полей изменение/снятие VIP блокируется.

## Проверки

```sh
node --check app.js
node tests/payment-methods.cjs
node tests/stars-checkout.cjs
node tests/info-faq.cjs
node tests/admin-users.cjs
node tests/payment-expiry.cjs
```

Нужен Playwright/Chromium, для установленного Chrome можно задать
`PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`. Провайдеры, бот и API в тестах подменены;
настоящих оплат, переходов к сторонним ботам или отправок пользователям нет.
Дополнительно перед выпуском проверить Android/iOS в Telegram, поворот экрана,
reduced motion, sandbox магазина и соответствующую выдачу/возвраты.

Полный браузерный прогон — **85 проверок без ошибок JavaScript**:
22 способа оплаты/Bottom Sheet, 12 Stars, 12 сроков оплаты, 20 FAQ и 19 админки.
Таймер дополнительно проверен визуально на ширине 320 и 440 px.

Backend PR №7 прошёл **204 offline-теста**, включая 25 deadline-проверок,
Stars, скидки/подписки, повторные платежи/webhook, возвраты, админку и рассылку.
Проверены точное применение патча и сохранность 95 остальных функций/классов,
`pip check`, компиляция и синтаксис Python 3.12. Runtime тестировался локально
на Python 3.14; это не запуск на Ubuntu/FirstVDS.

Во время review исправлены гонка старого Stars pre-checkout на границе срока,
ожидание SQLite дольше лимита ответа Telegram и голодание очереди проверки
платежей. В Mini App проверяются ID/провайдер/валюта/сумма, и поздний ответ
старого заказа не должен удалять новую попытку. Эти случаи закреплены тестами.

## Безопасная установка и откат — только после разрешения

1. Проверить актуальный сервер и его SHA. Backend нового PR содержит
   **комбинированный** патч с PR №6, доставкой бота и VIP. Не применять старый
   PR №6 повторно к уже подготовленному результату. Не устанавливать старый
   GitHub server.py. Использовать `prepare_unified_checkout.py` и manifest.
2. Сохранить приватный backup действующего кода, config.js, .env и SQLite;
   проверить backup API и `integrity_check`, учесть WAL. Не публиковать секреты.
3. После отдельного разрешения установить сначала совместимый backend:
   подготовленный из текущего исходника server.py, unified_payments.py,
   admin_vip.py, payment_deadlines.py. Не заменять Stars, XHTTP/Xray, broadcast/client-файлы и БД.
   Подробные команды и откат — `UNIFIED_CHECKOUT.md` и `BOT_CHECKOUT_VIP.md`
   серверного PR. Оставить ЮKassa выключенной.
4. Проверить bootstrap, Stars, /admin, /paysupport и прежний VPN-конфиг.
   Затем согласованно установить frontend app.js/index.html/style.css,
   публичные FAQ-настройки добавить отдельно без потери API URL.
5. Проверить нативную кнопку, оба состояния методов, reset FAQ, VIP grant/
   revoke, защищённые права, список/поиск/страницы и иконки. Проверить сохранение
   дедлайна при повторном входе и начисление подтверждённой поздней оплаты.
6. При откате вернуть сохранённый frontend и совместимый рабочий backend.
   Сохранить новые финансовые/VIP таблицы и историю, обработку незавершённых
   платежей; не восстанавливать старую БД поверх новых заказов/прав.

Этот PR не выполняет merge, deployment, перезапуск FirstVDS или включение
ЮKassa. Для этого требуется отдельное разрешение.
